# Память диктовки: до и после переноса

Цель переноса диктовки из отдельного приложения WhisperDictation в Cyclop —
не только один процесс вместо двух, а именно память: WhisperDictation держит
модель в памяти постоянно, с момента запуска и до выхода, вне зависимости от
того, пользуются им или нет. Цифры ниже — честный замер обеих сторон, снятый
руками 6 августа 2026 на том же маке (MacBook Air M4, macOS 26.5.2).

## Как замерено

Панель диктовки в собранном `Cyclop.app` пока не проверена вживую — она
просит Универсальный доступ, а выдавать его агенту нельзя. Поэтому воркер
гоняется напрямую, в обход хоткея и панели, ровно так же, как при его
разработке:

```bash
VENV=~/Library/Application\ Support/WhisperDictation/runtime/.venv/bin/python
WAV=~/Library/Application\ Support/WhisperDictation/recordings/dictation-20260718-213010.wav  # 14.6 с записи

mkfifo /tmp/worker_in
"$VENV" Resources/worker/cyclop_worker.py < /tmp/worker_in > /tmp/worker_out.jsonl 2>/tmp/worker_err.log &
WORKER_PID=$!
exec 3>/tmp/worker_in        # держит стдин воркера открытым между командами

footprint -p "$WORKER_PID" | tail -6      # 1: воркер запущен, модель не загружена

printf '{"cmd":"transcribe","path":"%s"}\n' "$WAV" >&3
# ждём строку в /tmp/worker_out.jsonl …
footprint -p "$WORKER_PID" | tail -6      # 2: сразу после распознавания

printf '{"cmd":"unload"}\n' >&3
# ждём вторую строку …
footprint -p "$WORKER_PID" | tail -6      # 3: после выгрузки по команде
```

Однострочный вариант из брифа (`printf '...\n...\n' | python worker.py`)
для замера не годится: `transcribe` и `unload` в нём улетают в стдин почти
одновременно, а между тремя состояниями нужно успеть вставить `footprint`.
FIFO с открытым на запись файловым дескриптором (`exec 3>...`) держит стдин
воркера живым и позволяет слать команды по одной, с паузами между ними —
то же самое поведение, просто управляемое по шагам.

Число, которое имеет значение — `phys_footprint` из вывода `footprint`: это
и есть то, что macOS показывает как реальную резидентную память процесса
(в отличие от `ps aux`/`RSS`, которые для процессов с Metal-выделениями MLX
занижают цифру на порядок — `ps` показывал 20 МБ RSS для того же
WhisperDictation, у которого `footprint` показывает 3254 МБ).

Воркер сам считает и сообщает освобождённое через `mlx.core`
(`get_active_memory` / `get_cache_memory`) в поле `freed_mb` каждого ответа —
это второй, независимый способ, и цифры сошлись: `footprint` до/после `unload`
разошёлся на 1618 МБ (1783 → 165), сам воркер в это же время отчитался о
`freed_mb: 1543.2`. Разница — это память интерпретатора и раннера,
`footprint`-у видимая, а `mx.core` не считающая, потому что она никогда не
принадлежала MLX.

## Результат

### Cyclop (`cyclop_worker.py`, модель грузится лениво при первой транскрипции)

| Состояние | `phys_footprint` | Комментарий |
|---|---|---|
| 1. Воркер запущен, модель не загружена | **8.4 МБ** | процесс поднялся, стдин ждёт первую команду — почти пустой интерпретатор |
| 2. Сразу после распознавания | **1783 МБ** | пик во время самого инференса — **2980 МБ**; воркер сам вызывает `mx.clear_cache()` сразу после каждой транскрипции (см. `Engine.transcribe`), поэтому к моменту замера кэш уже частично сброшен |
| 3. После явной выгрузки (`{"cmd":"unload"}`) | **165 МБ** | `Engine.unload()` обнуляет `ModelHolder.model`, чистит кэш MLX — см. ниже, что осталось за пределами этой чистки |

Ответы воркера за этот прогон:

```json
{"text": "А еще сам чат мне ответил как-то странно, какие-то квадратные скобочки, что-то такое не для юзера, а что-то техническое как будто бы. Это тоже плохо, так не должно быть.", "took": 4.177, "freed_mb": 1195.7}
{"unloaded": true, "freed_mb": 1543.2}
```

**Ориентир из плана задачи был «меньше 100 МБ» — не выполнен, вышло 165 МБ,
на две трети больше.** Это честный результат, не приукрашенный, и вот из чего
он состоит.

Отдельным прогоном измерено, сколько памяти стоит сам факт импорта тех же
библиотек, что использует воркер (`mlx.core`, `mlx_whisper`, `numpy`,
`huggingface_hub` — то, что тянет за собой `transcriber._ensure_backend()`),
**без единой загрузки весов модели**:

```
$ python -c 'from whisper_dictation.config import load_config; \
             from whisper_dictation.transcriber import WhisperTranscriber; \
             t = WhisperTranscriber(load_config().whisper); \
             t._ensure_backend()'
phys_footprint: 120 МБ
```

То есть **120 МБ из 165 — это цена самого импорта**, до того, как в процесс
попал хоть один байт весов: интерпретатор Python, рантайм MLX (инициализация
Metal-устройства), numpy, huggingface_hub. Это происходит один раз за время
жизни воркера, при первой транскрипции, и дальше не растёт независимо от
того, сколько раз потом грузить и выгружать модель.

Оставшиеся **~45 МБ** (165 − 120) — то, что не отдаёт назад именно цикл
загрузки/выгрузки весов. Раскладка `footprint` по категориям для процесса
после выгрузки:

```
  81 MB  MALLOC_SMALL
  62 MB  untagged (VM_ALLOCATE)
  41 MB  __TEXT (clean, разделяемый код — .so/.dylib mlx/mlx_whisper/numpy)
9552 KB  __DATA_CONST
6832 KB  MALLOC_LARGE
4970 KB  __DATA
...
 171 MB  TOTAL
```

`mx.clear_cache()` и `unload()` освобождают только буфер массивов MLX — тот
же, что считают `mx.get_active_memory()`/`get_cache_memory()`. Скомпилированные
Metal-шейдеры и argument-энкодеры, которые GPU-раннер держит для повторного
использования между вызовами, в этот счётчик не входят и `clear_cache()` их
не трогает — отсюда и расхождение между тем, что заявляет сам MLX
(`freed_mb: 1543.2`), и тем, что реально показывает ОС (`footprint`: разница
1783 → 165, то есть 1618 МБ). Дальше ужимать особо нечего: это не утечка,
которая растёт с каждой транскрипцией (см. ниже — повторный `unload`
показывает то же самое число), а разовая стоимость факта, что Metal/MLX хоть
раз запускались в этом процессе.

### Реальная выгрузка по простою (не по команде, а по таймеру)

Дальше это же самое — уже без явного `unload`, вживую, ожиданием тех же 600 с
(`Engine.IDLE_SECONDS`), которые использует `Engine.maybe_unload_idle()` в
реальной работе. Воркер запущен, отправлена одна транскрипция, дальше — только
ожидание, без единой команды в стдин:

```
TRANSCRIBE_SENT_EPOCH = 1786012056
AUTO-UNLOAD DETECTED at epoch  1786012685   (через 629 с ≈ 10 мин 29 с)
{"unloaded": true, "freed_mb": 1543.2}
phys_footprint после авто-выгрузки: 171 МБ (пик 2986 МБ)
```

629 с — это ожидаемо больше 600: `_idle_watch` проверяет простой раз в 30 с
(`time.sleep(30)` в цикле), а не мгновенно по истечении таймаута, так что
реальное срабатывание всегда попадает в окно 600–630 с. Число почти совпало
с замером по явной команде (171 МБ против 165 МБ) — разница на уровне шума
между прогонами: `maybe_unload_idle()` в коде воркера дублирует тело
`unload()` целиком (чтобы не брать `RLock` повторно, пока он уже держится
вызывающим циклом), так что путь один и тот же, только повод разный.

### WhisperDictation (старое приложение, работает прямо сейчас — не трогалось)

| Состояние | `phys_footprint` | Комментарий |
|---|---|---|
| единственное — процесс держит модель всё время | **3254 МБ** (пик 3345 МБ) | PID 6163, `python -u -m whisper_dictation.app`, запущен 4 августа в 11:37, то есть работает **2 суток 1.5 часа** без единой транскрипции за это время (последняя запись в `~/Library/Application Support/WhisperDictation/recordings/` — от 31 июля). Число не меняется ни от простоя, ни от использования: приложение не выгружает модель никогда, состояний «до загрузки» и «после выгрузки» у него просто не существует |

Два независимых замера `footprint -p 6163`, снятые с разницей в несколько
минут, дали одно и то же число — 3254 МБ, что подтверждает: это не
случайный всплеск, а именно установившееся, постоянно занятое состояние.

## Итог

| | WhisperDictation | Cyclop |
|---|---|---|
| Простаивает сутками | 3254 МБ — всегда | 0 МБ, если ни разу не диктовали — `cyclop_worker.py` поднимается лениво из `TranscriberBridge.transcribe()` при первой транскрипции, а не при старте приложения; ~8 МБ в первые секунды после запуска, пока модель ещё не загружена |
| Во время диктовки | 3254 МБ — не меняется | до 2980 МБ на пике |
| Через ~10.5 минут простоя после диктовки | 3254 МБ | 171 МБ — живой замер реальной выгрузки по таймеру простоя (см. выше), не по команде |

Пиковое потребление во время самой транскрипции у Cyclop сопоставимо со
старым приложением (обе используют одну и ту же модель large-v3-turbo через
MLX — движок и промпт не менялись, см. `whisper_dictation.config`). Разница
не в пике, а в том, что происходит после: WhisperDictation остаётся на пике
навсегда, Cyclop возвращается к сотне с небольшим мегабайт через 10–10.5
минут простоя (что подтверждено живым замером, а не только чтением кода) и
к нулю, когда всё приложение не запущено.
